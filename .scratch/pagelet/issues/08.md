## What to build

Operators deploy behind HTTPS reverse proxies without losing effective client-IP limits or trusting forged forwarding headers.

Delivery phase: 1 — API, raw access, OpenAPI, and CLI.

## Acceptance criteria

- [ ] Support explicit external-URL configuration and trusted proxy IP/CIDR configuration, trusting no proxies by default.
- [ ] Resolve X-Forwarded-For right-to-left from the connected peer, skip explicitly trusted proxies, and use the first untrusted address; ignore forwarding headers from untrusted peers.
- [ ] Apply the resolved client IP to both account-login and page-password rate limits, retaining target-level limits across different source IPs.
- [ ] Choose and document conservative handling of malformed forwarding information without allowing client-controlled bypass.
- [ ] Document ingress header replacement/correct append requirements, HTTPS termination and browser cookie/CSRF deployment behavior.
- [ ] Test direct and forged-header clients, single/multiple trusted proxies, untrusted intermediaries, CIDRs and HTTP 429 behavior; update API deployment documentation.

## Testing approach

Test observable behavior, using the HTTP boundary with real temporary SQLite as the primary seam, executable CLI smoke tests where applicable, and browser tests for web behavior. Keep authorization and persistence real rather than mocking business rules. Update the public OpenAPI contract alongside every affected API operation. Follow the parent specification and accepted domain decisions; do not add deferred features.
