## What to build

Owners protect pages, while visitors verify a password once to read that page through API and raw access for 24 hours.

Delivery phase: 1 — API, raw access, OpenAPI, and CLI.

## Acceptance criteria

- [ ] Accept page passwords of 1–128 Unicode characters without rewriting; an empty value removes protection. Store irreversible verifiers and require the page version for password changes.
- [ ] Apply identical authorization to API and raw reads; owners and administrators bypass passwords, while unauthorized responses reveal only that a password is required.
- [ ] After password verification, issue a 24-hour page-scoped read-only grant: a dedicated request header for scripts and an HttpOnly cookie for browsers, never URL credentials.
- [ ] Password changes/removal revoke all previous page grants; deletion removes grants. Bind grants to immutable page identity so slug reuse cannot authorize another page.
- [ ] Do not cache content responses or grant-issuance responses; access policy changes do not claim to recall content already delivered.
- [ ] Rate-limit password verification by direct source IP and target page with process-local HTTP 429 responses; reuse established abuse-control behavior.
- [ ] Test visitors/owners/other users/administrators across API and raw reads, metadata hiding, expiry, revocation, multiple page grants, and denial of mutation through grants; extend OpenAPI.

## Testing approach

Test observable behavior, using the HTTP boundary with real temporary SQLite as the primary seam, executable CLI smoke tests where applicable, and browser tests for web behavior. Keep authorization and persistence real rather than mocking business rules. Update the public OpenAPI contract alongside every affected API operation. Follow the parent specification and accepted domain decisions; do not add deferred features.
