## What to build

Operators run one executable containing the complete API and web experience and can verify the supported workflows and operational procedures.

Delivery phase: 2 — browser interface and embedded release.

## Acceptance criteria

- [ ] Verify /<slug>, /_/raw/<slug>, /_/api/v1/*, /_/app/*, /_/openapi.json and /_/assets/* routing from the final executable without loose frontend runtime files.
- [ ] Exercise visitor, owner, other-user and administrator browser journeys including preview, GFM, password grants, transfer, credential rotation and permanent deletion.
- [ ] Verify malicious Markdown cannot execute scripts or obtain credentials and that browser paths cannot bypass API authorization.
- [ ] Re-run the meaningful HTTP/SQLite, CLI and browser suites, including proxy deployment, persistence, migration and stopped-service backup/restore checks.
- [ ] Complete end-user/operator documentation for JavaScript-dependent reading, trusted administrators, reusable slug risks, data backups and permanent deletion.
- [ ] Confirm both delivery phases are complete without adding deferred features or invented performance acceptance thresholds.

## Testing approach

Test observable behavior, using the HTTP boundary with real temporary SQLite as the primary seam, executable CLI smoke tests where applicable, and browser tests for web behavior. Keep authorization and persistence real rather than mocking business rules. Update the public OpenAPI contract alongside every affected API operation. Follow the parent specification and accepted domain decisions; do not add deferred features.
