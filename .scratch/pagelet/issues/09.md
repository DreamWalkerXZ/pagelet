## What to build

An operator can use the executable and documented API to run the complete first-phase service and safely upgrade or restore its data.

Delivery phase: 1 — API, raw access, OpenAPI, and CLI.

## Acceptance criteria

- [ ] Run the initialized executable through user creation, publication, raw reading, password protection, credential rotation, ownership transfer and account/page deletion.
- [ ] Validate the complete public OpenAPI document at /_/openapi.json against actual request/response behavior, security alternatives and errors including 409 and 429.
- [ ] Document deployment configuration, trusted proxies, administrator recovery and the separation between executable and persistent data.
- [ ] Demonstrate stopped-service backup and restore of the entire data directory, forward migrations and safe refusal of newer schemas; require pre-upgrade backups and promise no downgrade.
- [ ] Run the agreed HTTP/SQLite and CLI suites; verify no public enumeration, anonymous publication, backend HTML rendering or out-of-scope account operations.
- [ ] Clearly mark this as API-phase completion, with public reading/editor/management UI still delivered by the second phase.

## Testing approach

Test observable behavior, using the HTTP boundary with real temporary SQLite as the primary seam, executable CLI smoke tests where applicable, and browser tests for web behavior. Keep authorization and persistence real rather than mocking business rules. Update the public OpenAPI contract alongside every affected API operation. Follow the parent specification and accepted domain decisions; do not add deferred features.
