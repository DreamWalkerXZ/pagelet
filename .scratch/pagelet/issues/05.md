## What to build

Users establish browser sessions, manage their password or token, and recover access through administrators or the local CLI.

Delivery phase: 1 — API, raw access, OpenAPI, and CLI.

## Acceptance criteria

- [ ] Provide username/password login and current-session logout using separate HttpOnly cookies, expiring seven days after login without renewal.
- [ ] Protect cookie-authenticated mutations against CSRF; do not require browser storage of account API tokens.
- [ ] Support self-service password changes, administrator password resets, and administrator recovery through the local CLI.
- [ ] Password changes/resets rotate the API token and immediately revoke all account sessions; expose the replacement token only in the credential issuance response.
- [ ] Users and administrators can reset a user's single API token; revoke the old token immediately without logging out web sessions. Tokens otherwise have no automatic expiry.
- [ ] Rate-limit login by direct source IP and target account with process-local counters, HTTP 429, and no permanent account lockout; proxy-aware source resolution follows in its own slice.
- [ ] Test expiry with controlled time, token disclosure/revocation, session isolation, CSRF, password validation, login limits and CLI recovery; extend OpenAPI.

## Testing approach

Test observable behavior, using the HTTP boundary with real temporary SQLite as the primary seam, executable CLI smoke tests where applicable, and browser tests for web behavior. Keep authorization and persistence real rather than mocking business rules. Update the public OpenAPI contract alongside every affected API operation. Follow the parent specification and accepted domain decisions; do not add deferred features.
